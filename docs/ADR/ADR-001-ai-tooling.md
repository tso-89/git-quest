# ADR-001: AI Tooling — One Shared Rules File, Four Agent Platforms

**Date:** 2025-01-01
**Status:** Accepted

---

## Context

This project uses AI coding assistants heavily throughout the development lifecycle — for feature implementation, code review, debugging, security audits, and documentation. We needed to decide on a standard AI tooling configuration to ensure consistent, high-quality AI assistance across the team.

The key requirements were:
1. AI agents must follow consistent coding conventions without constant re-prompting.
2. Specialised agents should handle specific tasks (review, test, debug) rather than using a single general-purpose agent.
3. Configuration must be portable — any developer cloning the repo gets the same AI setup.
4. The setup should work with multiple IDEs (VS Code, Cursor, Windsurf, JetBrains).

---

## Decision

**`AGENTS.md` is the single source of truth.** Every supported platform reads it — natively
where possible, by generated mirror where not. No rule is written twice.

| Platform | Reads shared rules via | Platform-specific config |
|----------|------------------------|--------------------------|
| **Claude Code** | `CLAUDE.md` imports `AGENTS.md` | `.claude/` (agents, skills, commands, rules, settings) |
| **Codex** | reads `AGENTS.md` natively | skills inlined as a marked block in `AGENTS.md` |
| **OpenCode** | reads `AGENTS.md` natively | `opencode.json` + `.opencode/` |
| **Antigravity** | `GEMINI.md`, generated by inlining `AGENTS.md` | `.agents/skills/` |
| Cursor / Windsurf | `.cursorrules` / `.windsurfrules` point at `AGENTS.md` | none — rules only |

Platform capabilities differ and we do not pretend otherwise. Codex has no skills directory,
so its skills are inlined; Antigravity has no per-agent definition surface, so it gets none.
`template.manifest.json` records exactly what each platform receives.

---

## Rationale

**Why support four platforms instead of one?**
Developers pick their own tool, and that choice changes over time. Supporting several means
the project's conventions travel with the repository rather than with whoever set it up.

**Why one shared file instead of one file per platform?**
Hand-synchronised copies drift. The earlier version of this template kept three near-identical
rules files and they had already diverged — one silently lost an entire section. A single
source with generated mirrors makes drift impossible rather than merely discouraged, and CI
fails when a mirror is stale.

**Why dedicated skill/agent files per task?**
A single general-purpose "do everything" agent produces lower quality results than a focused agent with a narrow, well-defined role. Separate agents for coding, review, testing, debugging, security, and documentation allow each to have deep, domain-specific instructions and appropriate tool restrictions.

**Why commit AI config to the repo?**
AI configuration is as important as linting or testing configuration. Committed config:
- Ensures the whole team uses identical AI behaviour.
- Makes AI conventions reviewable and evolvable via PRs.
- Means new contributors get working AI setup immediately after `git clone`.

---

## Consequences

**Positive:**
- Consistent AI behaviour across the team.
- AI agents are aware of project architecture, conventions, and constraints from the first invocation.
- Specialised agents produce higher-quality outputs for their domain.
- AI config is version-controlled and auditable.

**Negative:**
- Slight overhead of maintaining two platform configs. Mitigated by: the `validate-ai-config.py` script and the `bootstrap-ai-project.py` script which keep them in sync.
- Requires developers to have at least one of the two platforms installed.

**Neutral:**
- Teams that only use one platform can ignore the other's directory — both are independently functional.

---

## Alternatives Considered

| Alternative | Why Rejected |
|-------------|-------------|
| Single AI platform only | Reduces flexibility; locks the team into one vendor's pricing and model quality |
| No committed config (ad-hoc prompting) | Inconsistent behaviour; knowledge not shared across team; every developer re-discovers conventions |
| Shared config via a git submodule | More complex to maintain; submodule versioning overhead not worth it at this scale |
